# Headscale Web 后台界面改造设计

- 日期：2026-08-26
- 状态：已确认
- 范围：连接成功后的后台界面
- 视觉方向：延续连接页的深色现代控制台风格
- 实施方式：共享后台组件 + 分页面改造

## 1. 背景

当前连接页已经形成深色、青绿色强调色和卡片式布局，但连接后的 Dashboard、Users、Nodes、Routes、PreAuth Keys 和 Settings 仍接近功能原型：公共布局高度不足，多数列表使用无样式的原生表格和按钮，深色主题下视觉不一致，工具栏、状态、危险操作和移动端缺少统一处理。

实际只读检查确认 Headscale 0.29.3 的版本、健康状态和各列表读取正常，问题集中在前端表现层，而不是 API、Repository 或 Query 数据链路。

## 2. 目标

1. 让登录后的全部页面延续连接页的视觉语言。
2. 建立少量、明确、可复用的后台界面组件。
3. 统一页面标题、工具栏、指标卡片、状态、表格、空状态和危险确认。
4. 保持现有 API、Repository、Mapper、Query 和 Mutation 边界不变。
5. 支持深色主题、浅色主题、移动端和键盘操作。
6. 禁止通过生产 Headscale 数据验证写操作；写操作使用 Mock 和自动化测试验证。

## 3. 非目标

- 不修改 Headscale API 契约。
- 不重构 Repository、Mapper 或领域模型。
- 不增加 ACL、API Key 管理、多实例或服务端能力。
- 不建立大型通用设计系统或独立组件包。
- 不在本次改造中改变产品的信息架构和顶级导航项。

## 4. 方案选择

采用“共享后台组件 + 分页面改造”。

不采用纯 CSS 修补，因为原生表格、按钮和危险操作的结构问题无法通过样式可靠解决。不采用完整设计系统，因为当前项目规模不需要大量抽象，容易增加维护成本。

## 5. 视觉规范

### 5.1 风格

- 深色专业控制台作为主要视觉基线。
- 青绿色作为品牌色和主要操作色。
- 页面背景、侧边栏、顶栏、卡片和浮层形成清晰层级。
- 使用低饱和边框和阴影，避免大面积高对比纯黑。
- 字号、间距、圆角和控件高度保持统一。
- 不依赖颜色单独表达状态，同时显示文本或图标。

### 5.2 主题

共享组件使用统一的 CSS 变量或 Naive UI 主题 token，不在各页面重复硬编码颜色。深色为设计基线，浅色主题保持同样的信息层级和对比度。跟随系统主题继续使用现有设置模型。

### 5.3 响应式

- 桌面端使用固定侧边栏、顶栏和内容区。
- 小屏幕隐藏固定侧边栏，通过抽屉菜单导航。
- 工具栏在窄屏垂直排列。
- 数据表格在窄屏提供横向滚动，不隐藏关键状态和危险操作信息。
- 指标卡片根据宽度从多列降为双列或单列。

## 6. 公共布局

### 6.1 AppShell

`AppShell` 负责完整视口高度和后台页面结构：

- 根布局最小高度为 `100vh`，消除内容下方白色区域。
- 侧边栏保持稳定宽度，并为移动端提供抽屉。
- 顶栏在桌面端固定信息层级，在窄屏允许合理换行或折叠。
- 主内容区设置统一背景、内边距和内容最大宽度。
- 路由页面只负责自身内容，不重复定义外层间距。

### 6.2 AppNav

- 增加产品标识区。
- 每个导航项使用图标、文本和清晰选中态。
- 保留 Dashboard、Users、Nodes、Routes、PreAuth Keys、Settings 六个入口。
- 移动端选择路由后关闭抽屉。

### 6.3 StatusBar

- 实例地址以截断文本或紧凑标识展示，完整值可通过 title/tooltip 查看。
- 版本和数据库健康状态使用状态标识。
- 刷新、语言和主题为次级操作。
- 断开连接与普通刷新操作保持视觉区分。
- 小屏幕减少非必要文本，但保留状态语义和可访问名称。

## 7. 共享组件

共享组件放在 `src/components` 或清晰的共享 UI 目录中。组件只处理展示和交互外壳，不直接访问 Repository、Query 或 Store。

### 7.1 PageHeader

职责：

- 页面标题和简短说明。
- 可选的主要操作区。
- 统一页面顶部间距和响应式排列。

### 7.2 PageToolbar

职责：

- 搜索、筛选、刷新和页面级操作。
- 桌面端横向排列，移动端垂直排列。
- 不包含业务筛选逻辑，只通过 props 和事件通信。

### 7.3 StatCard

职责：

- 展示指标标题、数值、图标和可选状态。
- 支持 loading 和不可用值。
- Dashboard 使用统一网格承载。

### 7.4 DataTable

优先封装 Naive UI DataTable 的公共展示配置，而不是继续使用原生 `<table>`：

- 统一表头、行高、边框和 hover 状态。
- 支持 loading、empty 和横向滚动。
- 业务页面继续定义自己的列和单元格渲染。
- 不在共享组件内实现业务排序、筛选或 Mutation。

### 7.5 StatusBadge

统一展示：

- 在线 / 离线。
- 健康 / 异常。
- Advertised / Approved / Serving。
- Active / Used / Expired。

每个状态同时包含文本和视觉标记。

### 7.6 EmptyState

展示空数据、加载失败和可选恢复操作。主错误文案来自 i18n，不直接显示服务端异常作为唯一信息。

### 7.7 ConfirmDialog

统一危险操作确认：

- 说明将影响的资源和操作结果。
- 删除用户、删除节点继续要求输入名称。
- 过期 Key、删除 Key、立即过期节点、取消路由审批至少要求明确确认。
- 确认期间禁用重复提交。
- 关闭后恢复合理焦点。

## 8. 页面设计

### 8.1 Dashboard

- 使用 `PageHeader` 和指标卡片网格。
- 指标包括版本、数据库、用户、节点、在线/离线节点、路由和 PreAuth Key。
- 增加异常或待处理资源区域：离线节点、即将过期节点、待审批路由和即将过期 Key。
- 数据继续来自已有 Query，不增加重复 API 请求。

### 8.2 Users

- 顶部为标题、说明和创建按钮。
- 工具栏包含搜索和 Provider 筛选。
- 使用统一 DataTable 展示名称、显示名、邮箱、Provider 和创建时间。
- 点击用户进入详情抽屉；重命名和删除在抽屉内分区。
- 删除展示关联节点数量并保留名称确认。

### 8.3 Nodes

- 工具栏包含搜索和在线状态筛选。
- 表格使用状态徽章，并合理展示名称、用户、IP、标签、路由、最后在线和过期时间。
- 多个 IP 和标签使用紧凑列表或 Tag，避免直接拼接长文本。
- 详情抽屉按概览、网络、标签、过期策略和危险操作分组。
- 删除和立即过期必须使用确认流程。

### 8.4 Routes

- 工具栏保留全部、待审批、已审批、Exit Node 和普通子网筛选。
- Advertised、Approved、Serving 使用独立状态徽章。
- 审批与取消审批保留节点级并发锁。
- 取消审批增加确认，避免在生产环境中误触。
- Exit Route 的 IPv4/IPv6 成组行为保持现有领域逻辑。

### 8.5 PreAuth Keys

- 工具栏包含状态筛选和创建按钮。
- 表格展示 Key 预览、用户、状态、过期时间和操作。
- 已失效资源的不可用操作需要禁用或隐藏。
- Expire 和 Delete 均使用确认流程。
- 创建后的明文 Key 继续只存在于组件内存，关闭弹窗后销毁。

### 8.6 Settings

设置页分为三个卡片区：

1. 连接：Headscale URL、API Key、凭据保存方式、测试连接。
2. 刷新：自动轮询和轮询间隔。
3. 外观：语言、主题和日期时间格式。

保存操作置于明确的页面操作区。断开连接作为独立危险区域展示，避免与普通保存按钮并列混淆。

## 9. 数据流与状态

- 页面继续通过现有 Vue Query composable 读取数据。
- Mutation 接口和缓存失效策略保持不变。
- 共享 UI 组件只接收数据、状态和事件。
- 筛选、选择项、抽屉和弹窗状态留在页面组件本地。
- Pinia 继续只管理连接和客户端设置。

## 10. 错误与反馈

- 初次加载显示骨架或 Spin，避免布局突然跳动。
- 页面级读取失败使用 `EmptyState` 或 Alert，并提供重试。
- Mutation 成功继续使用简短 Message。
- Mutation 失败使用 Notification，保留表单输入。
- 危险操作提交期间锁定确认按钮。
- 401 处理和返回连接页逻辑保持现状。

## 11. 安全约束

- 不在 UI、日志、测试快照或错误文本中暴露完整 API Key。
- 不在真实生产 Headscale 上执行创建、修改、删除、审批或过期测试。
- 所有写操作通过 MSW、组件测试和 E2E Mock 验证。
- 生产只读检查仅允许页面导航和 GET 请求。
- 临时认证文件、浏览器状态和包含生产数据的截图不得提交 Git。

## 12. 可访问性

- 导航、表格、表单和弹窗保持明确的可访问名称。
- 图标按钮提供 `aria-label`。
- 状态不只依赖颜色。
- 抽屉和确认框正确管理焦点。
- 键盘可完成导航、筛选和核心操作。
- 尊重 `prefers-reduced-motion`。
- 深浅主题均满足基础对比度要求。

## 13. 测试策略

- 共享组件测试：渲染、状态、事件和响应式语义。
- Shell 测试：导航、移动菜单、断开连接和状态展示。
- 页面组件测试：loading、empty、error、success、筛选和确认流程。
- Mutation 测试全部使用 MSW，不连接生产环境。
- Playwright 使用本地 Mock Headscale 验证主要页面和移动端布局。
- 最终进行桌面端、平板和手机视口的浏览器视觉检查。

## 14. 完成标准

1. 登录后所有页面使用统一后台布局和视觉语言。
2. 页面在深色主题下不再出现原生白色按钮或底部白色区域。
3. 所有列表使用统一表格外观，并在窄屏可访问。
4. Dashboard、Users、Nodes、Routes、PreAuth Keys 和 Settings 完成约定布局。
5. 危险操作均有确认，不会单击后直接提交。
6. 中英文、深浅主题和移动端均可用。
7. 现有 API 和数据层行为不被改变。
8. 自动化测试、类型检查、Lint 和生产构建通过。
9. 验证过程不对生产 Headscale 执行写操作。

## 15. 后续步骤

本文件仅定义已确认的界面改造设计。本次不生成实施计划，不开始代码实现。实施计划需由用户后续明确授权后另行编写。
